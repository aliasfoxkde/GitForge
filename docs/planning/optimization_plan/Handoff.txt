# GitForge — Comprehensive Production Readiness & Optimization Handoff

**Repository:** `aliasfoxkde/GitForge`  
**Primary branch:** `main`  
**Initiative:** Production hardening, execution efficiency, storage optimization, incremental CI and operational reliability  
**Umbrella:** [GitForge #342](https://github.com/aliasfoxkde/GitForge/issues/342)  
**Architecture PR:** [#343](https://github.com/aliasfoxkde/GitForge/pull/343)

# 1. Mission and execution requirements

Take ownership of bringing GitForge to a production-ready state, resolving outstanding implementation, reliability, security, performance and operational issues.

This is an end-to-end engineering initiative. Do not stop after writing plans, creating issues, or documenting recommendations. Implement the work, test it, resolve regressions, consolidate branches, submit reviewable PRs, and verify the resulting production behavior.

The overarching objectives are:

1. Make GitForge reliable under high concurrency and multiple simultaneous projects.
2. Eliminate unnecessary queued work, duplicate CI execution, redundant builds and repeated dependency downloads.
3. Reduce CPU, RAM, disk I/O, storage consumption, network transfers and latency.
4. Implement intelligent incremental testing and build-result reuse without compromising correctness.
5. Introduce safe content-addressed storage and managed workspaces.
6. Separate lightweight, latency-sensitive work from resource-intensive workloads.
7. Improve scheduler fairness, resource governance, recovery and observability.
8. Optimize API, database and service execution for small VPS deployments.
9. Improve the architecture so new languages, test runners, compilers and execution backends can be integrated without rewriting GitForge.
10. Consolidate outstanding PRs, resolve merge conflicts, close duplicate work, and eliminate stale branches safely.
11. Establish reliable CI/CD, security, release and rollback procedures.
12. Deliver a system that can onboard real repositories and handle concurrent customer workloads.

## Non-negotiable engineering rules

- Preserve working functionality and existing architecture unless a measured improvement justifies changing it.
- Prefer small, independently reviewable implementation PRs.
- Do not create competing implementations of functionality that already exists.
- Do not introduce arbitrary concurrency restrictions without measuring the workload.
- Do not disable, weaken or bypass required security, testing or quality gates to obtain green CI.
- Do not claim a feature is implemented merely because the code compiles.
- Do not merge or deploy based on stale validation results.
- Do not delete dirty worktrees, unmerged changes, user data or artifacts without verified ownership and recovery procedures.
- Do not globally share writable state between unrelated jobs or trust domains.
- Do not let AI-generated summaries replace authoritative source records.
- Preserve backward compatibility where practical and use explicit versioning where contracts must change.
- Every optimization must have before/after measurements.
- Every new capability must have automated tests, failure handling, documentation and an operational rollback procedure.

**Work continuously through the phases below. Do not stop at the first milestone.** If an implementation depends on unavailable infrastructure, implement the parts that can be validated, document the exact blocker, and continue with independent work.

# 5. Phase 2 — Resource-aware queueing and execution

Implement #338, coordinating #277 and #284.

This is one of the highest-priority architectural changes because it addresses the overload problem directly.

## 5.1 Separate control and execution capacity

GitForge should distinguish control-plane operations from execution jobs.

Control-plane operations include:

- Authentication.
- Git requests and ref updates.
- Trigger persistence.
- Webhooks.
- Runner heartbeats.
- Cancellation.
- Queue inspection.
- Job status retrieval.
- Artifact metadata and receipt access.

These should remain responsive even during heavy build activity.

No expensive compilation, dependency installation, archive extraction or large filesystem traversal should run synchronously on API request paths.

## 5.2 Implement workload classes

Introduce the following logical lanes:

| Lane | Examples |
|---|---|
| Control | API, auth, Git, webhooks, heartbeat, cancellation |
| Fast | Formatting, metadata, changed-file lint, targeted unit tests |
| Standard | Ordinary builds and affected test suites |
| Heavy | Full workspace tests, coverage, fuzzing, releases |
| Background | Cache warming, graph refresh, GC, compaction |

Use a unified durable execution and job-lease model. These should be scheduling policies, not separate disconnected job-management implementations.

## 5.3 Scheduling algorithms

Extend the existing priority and repository-aware scheduler.

Implement:

- Weighted fair scheduling between repositories and tenants.
- Per-repository concurrency limits.
- Bounded fast-lane reserved capacity.
- Priority aging.
- Anti-starvation guarantees.
- Per-lane resource budgets.
- Bounded pending queues.
- Backpressure under overload.
- Resource-aware runner selection.
- Cancellation and retry preservation.
- Durable queue-reason reporting.

Avoid an approach where a permanent fast-lane workload starves heavy jobs indefinitely.

Likewise, a backlog of large projects must not block short validation or control-plane activity.

## 5.4 Resource-aware admission

Each execution should have an explicit resource request and enforced limit.

Cover:

- CPU quota.
- Memory reservation and maximum.
- Process count.
- Scratch/workspace capacity.
- Disk/inode headroom.
- I/O pressure.
- Network policy.
- Timeout.
- Runner and toolchain requirements.

Collect host and per-container metrics, including cgroup resource usage and Linux PSI where available.

Admission decisions must account for:

1. Existing running workloads.
2. Available runner slots.
3. CPU and memory headroom.
4. Available scratch space.
5. Storage pressure.
6. Current I/O contention.
7. Repository and tenant concurrency.
8. The requested job's resource class.

If capacity is insufficient, defer work with a meaningful reason:

```text
runner_unavailable
cpu_budget
memory_headroom
scratch_headroom
io_pressure
per_repository_limit
lane_limit
dependency_wait
```

Do not kill otherwise healthy jobs just because pressure increases. Prevent additional work from entering an unsafe environment.

## 5.5 Actions and GitForge integration

Resolve #284.

Map every GitHub Actions workflow to:

- Its real commands.
- Runner requirements.
- Resource costs.
- Equivalent GitForge pipeline jobs.
- Required status checks.
- Security responsibilities.

Avoid running the same expensive tests once through Actions and again through GitForge when both executions validate the same commit and contract.

Keep Actions as an integration/status adapter where possible and GitForge as the execution source of truth where appropriate.

Do not remove independent checks simply because they look similar.

Use one canonical execution identity to correlate:

```text
repository
commit
ref
pipeline-definition digest
trust class
trigger
execution ID
required gate
```

GitHub must report the actual result of the associated GitForge execution.

## 5.6 Queue observability

Expose:

- Queue depth by lane.
- Queue age.
- Queue wait time.
- Deferral reason.
- Running jobs.
- Per-repository utilization.
- Per-runner utilization.
- CPU-seconds.
- Peak RAM.
- Disk usage.
- I/O bytes.
- Cache efficiency.
- Execution latency.
- Failed and recovered leases.

The queue must explain why a job is waiting instead of merely displaying `queued`.

**Exit criteria:** mixed workloads make fair progress, fast checks remain responsive, heavy work is bounded, and every deferral is explainable.

# 6. Phase 3 — Shared storage, CAS and managed workspaces

Implement #339.

The goal is to eliminate repeated storage and filesystem work throughout GitForge, not merely introduce more symlinks.

## 6.1 Content-addressed storage

Implement an immutable CAS for non-Git content.

Do not replace Git's native object database. Keep Git responsible for its own commits, trees and blobs.

Use CAS for:

- Shared dependency snapshots.
- Build outputs.
- Immutable workspace bases.
- Compiler artifacts.
- Test result artifacts.
- Execution manifests.
- Container/build metadata.
- Logs and debug chunks.
- Impact graph artifacts.
- Knowledge summaries.

Each object should have:

- A complete cryptographic digest.
- Size.
- Type and schema version.
- Trust namespace.
- Integrity status.
- Creation metadata.
- Reference information.
- Retention/lease information.

Use canonical, unambiguous cache-key serialization. Avoid concatenating arbitrary strings without delimiters or using truncated digests as unique identities.

Use the existing SHA-256 dependency unless a benchmark and compatibility assessment justify a different algorithm.

## 6.2 Deduplication

Deduplicate at ingest.

Byte-identical objects within an authorized namespace should reference the same stored object.

Evaluate:

- Whole-file hashing.
- Content-defined chunking for large archives/logs.
- Compression.
- Existing Git object reuse.
- Package-manager content stores.
- Compiler output reuse.

Do not enable chunking everywhere automatically. Hashing and indexing overhead can exceed the savings for small files.

Track logical versus physical storage and real deduplication ratios.

## 6.3 Cache identity and correctness

Include relevant execution inputs:

- Source tree.
- Lockfiles.
- Dependency graph.
- Compiler/toolchain.
- Target triple.
- OS/architecture.
- Runtime ABI.
- Runner image digest.
- Build flags/features.
- Pipeline configuration.
- Test arguments.
- Relevant environment contract.

Different toolchain images must not accidentally share incompatible compiled outputs.

Replace the current sanitized image-string cache naming with a canonical image identity digest.

Use explicit manifests and durable references instead of relying on directory naming conventions alone.

## 6.4 Worktree/workspace manager

Build a reusable workspace manager.

Suggested backend priority:

1. Native Git worktrees.
2. Reflink-based copy-on-write.
3. OverlayFS.
4. Btrfs subvolume snapshots.
5. Safe full-copy fallback.

Provide a common provider interface so the underlying filesystem can change without changing job execution logic.

Track:

- Workspace ID.
- Repository.
- Commit.
- Branch/ref.
- Owner.
- Agent/session.
- Job association.
- Lease.
- State.
- Filesystem provider.
- Base digest.
- Creation and last-used times.
- Cleanup policy.

Lifecycle states:

```text
creating
active
idle
pinned
collecting
deleted
```

Workspace creation, ownership and cleanup must be durable and lease-aware.

### Critical storage rules

- Do not hard-link mutable build output.
- Do not symlink writable target directories into a shared store.
- Shared immutable content must be protected from modification.
- Unrelated jobs must not concurrently mutate the same Cargo target directory.
- Keep per-job writable build state isolated.
- Validate filesystem capabilities before using specialized providers.

Btrfs snapshots should be optional and only used when the filesystem layout supports them. They do not replace backups.

## 6.5 Garbage collection

Implement a proper storage GC.

Use:

1. Mark live references.
2. Include active job/workspace leases.
3. Include pinned releases and recovery artifacts.
4. Generate dry-run results.
5. Quarantine eligible objects.
6. Wait through a grace period.
7. Recheck references and leases.
8. Delete only verified unreferenced objects.

Protect against the publish-to-reference race. An object must not become eligible for deletion between writing its contents and registering its durable reference.

Add:

- Per-tenant quotas.
- Cache budgets.
- Retention policies.
- Pressure thresholds.
- Manual pin/unpin.
- Orphan reconciliation.
- Corruption checks.
- Recovery procedures.

Never automatically remove a dirty or owned workspace.

## 6.6 Storage observability

Provide metrics:

```text
logical_bytes
physical_bytes
deduplicated_bytes
dedup_ratio
cache_hits
cache_misses
cache_download_bytes
cache_write_bytes
workspace_bytes
snapshot_bytes
gc_candidates
gc_reclaimed_bytes
active_leased_bytes
corrupt_objects
```

Add a storage inspection and dry-run GC CLI.

**Exit criteria:** shared objects are immutable and integrity-checked, workspace creation is safe, and GC cannot delete live work.

- Commits and source trees.
- Packages/crates.
- Modules/files.
- Functions/symbols where practical.
- Dependencies.
- Features.
- Tests and test binaries.
- Pipeline jobs.

```text

```

Do not create an elaborate graph database merely for the sake of abstraction. Start with the existing graph crate and a storage format appropriate to the scale of GitForge.

## 7.2 Build a test-impact index

Combine:

- Static dependency information.
- Cargo metadata.
- Project manifests.
- Build configuration.
- Coverage data.
- Execution traces.
- Test fixtures.
- Known integration dependencies.

Track which tests exercise which code.

Initially, file-level coverage mappings are acceptable where function-level mappings are unavailable. Improve precision incrementally.

## 7.3 Incremental execution

When a commit changes files:

1. Identify modified files.
2. Resolve their packages/modules.
3. Find dependent packages.
4. Determine affected tests.
5. Add new or modified tests.
6. Include affected integration/global tests.
7. Include previously failing and flaky tests.
8. Validate graph confidence.
9. Execute the selected tests.
10. Record the impact and execution evidence.

Use a conservative fallback whenever graph information is missing or uncertain.

## 7.4 Reusable test results

Implement a result cache keyed by the complete test fingerprint.

Include:

- Test identity.
- Source and dependency digests.
- Test binary and arguments.
- Fixtures.
- Environment.
- Compiler/runtime.
- Platform.
- Runner image.
- Configuration.
- Graph/index schema.

Only reuse deterministic, eligible test results.

Never assume that tests involving time, randomness, external services, mutable files or network calls are deterministic without capturing those inputs.

Never reuse:

- Newly added tests.
- Previously failing tests.
- Flaky tests.
- Tests with unknown inputs.
- Results from incompatible toolchains/environments.
- Results whose source dependencies changed.

Store result provenance and distinguish:

```text
executed_pass
executed_fail
cache_reused
flaky
timeout
skipped_by_selection
not_eligible
```

A cached result must never be reported as though the test executed in the current run.

## 7.5 Differential validation

This is mandatory.

During rollout, execute:

- The optimized selected test set.
- The full authoritative test set.

On the same commit.

Compare the results.

Any failure missed by the optimized selection blocks enabling that selection as an authoritative gate.

Measure the false-negative rate and target zero.

Keep scheduled full tests, coverage, fuzzing and full release validation.

## 7.6 OpenTestSuite integration

Use the existing OpenTestSuite prototype as the foundation for a versioned test-runner adapter.

The interface should support:

- Test discovery.
- Test selection.
- Execution.
- Retries.
- Test grouping.
- Resource requirements.
- Structured results.
- Logs.
- Coverage.
- Traces.
- Artifact publication.
- Test-result caching.
- Environment identity.

Integrate language-specific tools through adapters instead of building one monolithic GitForge test framework.

## 7.7 Rust-specific testing

Pilot `cargo-nextest`.

Requirements:

- Process isolation.
- Bounded test parallelism.
- Test groups.
- Serial-test support.
- Retry handling.
- Structured reports.
- Integration with durable receipts.

Retain Cargo and `cargo test` as compatible fallback paths.

**Exit criteria:** meaningful reduction in executed tests and CPU time without missed failures.

# 8. Phase 5 — Toolchain and compiler optimization

# 10. Phase 7 — Session, conversation, log and debug consolidation

Build on the CAS infrastructure from #339.

The goal is to significantly reduce storage consumed by repeated operational information while preserving recoverability.

## 10.1 Data representation

Keep original logs, conversations and execution records immutable.

Produce separate derived artifacts:

- Structured event streams.
- Command histories.
- Tool invocation records.
- Test outcomes.
- Error summaries.
- Debug traces.
- Decisions and constraints.
- Reusable knowledge.
- References to generated artifacts.

Use exact duplicate chunk elimination and compression before applying lossy summarization.

## 10.2 Knowledge extraction

Build a pipeline:

```text
raw source
    → normalization
    → exact deduplication
    → structured extraction
    → knowledge consolidation
    → retrieval indexing
    → provenance references
```

Summaries must retain source digests and exact offsets.

The original content must remain retrievable.

## 10.3 Compression target

Use 2% or less of original size as an aggressive experimental target, not a guaranteed production property.

Build a validation corpus measuring:

- Important fact recall.
- Decision preservation.
- Technical constraint preservation.
- Command/error preservation.
- Test-result preservation.
- Source traceability.
- Retrieval accuracy.

Never discard authoritative source data merely because an AI summary claims it is redundant.

Allow separate retention policies for raw logs, verbose debug traces, compressed event records and extracted knowledge.

**Exit criteria:** measured storage savings, validated retrieval, and preserved raw evidence.

# 11. Phase 8 — Comprehensive reliability and failure testing

Implement failure injection throughout the new architecture.

Required scenarios:

### Scheduler

- Multiple repositories flood the queue.
- Fast lane is saturated.
- Heavy jobs cannot obtain memory.
- A runner goes offline.

- Duplicate triggers arrive.

- Corrupt object.

- Concurrent garbage collection.

- Expired workspace with a stale lock.

### Testing

- Changed source invalidates old results.

- Failed/flaky test is never reused.
- Test dependency graph is incomplete.
- Toolchain changes.
- Environment changes.
- Cache checksum fails.

### Git and CI

- SSH push.

- Branch deletion.
- Duplicate webhook.
- Delayed outbox delivery.
- GitForge API 401.
- Worker restart.
- CI run recovery.
- Failed pipeline status reporting.
- Public fork PR isolation.

Every failure should produce a useful diagnostic, preserve durable state where required, and recover safely.

# 13. Required engineering workflow

Follow this workflow for every implementation task.

## Step 1 — Inspect

Review:

- Existing implementation.
- Related issues.
- Open PRs.
- Existing tests.
- Public APIs.
- Storage contracts.
- Database migrations.
- Configuration formats.
- Deployment assumptions.
- Backward compatibility.

Identify reusable code before writing anything new.

## Step 2 — Plan

Create a small implementation plan with:

- Files affected.
- Existing components reused.
- New components.
- API/schema changes.
- Risks.
- Migration strategy.
- Test strategy.
- Rollback plan.

Update the relevant GitHub issue.

## Step 3 — Implement

Use minimal, deliberate changes.

Avoid unnecessary dependencies and architectural rewrites.

Prefer shared libraries and adapters over duplicated implementations.

## Step 4 — Test locally

At minimum, run the relevant focused tests, then:

```bash
cargo fmt --all -- --check
cargo clippy --workspace --all-targets -- -D warnings
cargo test --workspace
```

Run applicable Python, shell, workflow, security, fuzz and integration checks.

Use the repository's existing authoritative commands and scripts rather than assuming these commands fully represent its CI configuration.

Check migrations, configuration parsing, release bundles and API compatibility.

## Step 5 — Integrate

Before opening or updating a PR:

```bash
git fetch origin
git rebase origin/main
```

Resolve conflicts semantically, not mechanically.

Inspect the resulting diff for:

- Lost functionality.
- Duplicate tests.
- Accidental configuration removal.
- Missing migration updates.
- Inconsistent API contracts.
- Changed defaults.
- Regressions in unrelated systems.

Run the tests again after the final conflict resolution.

## Step 6 — Submit PR

Every PR should include:

```text
Summary
Problem addressed
Implementation details
Files/components changed
Compatibility considerations
Tests performed
CI evidence
Performance measurements
Security implications
Migration instructions
Rollback instructions
Related issues
```

Keep PR scope focused.

## Step 7 — Validate exact commit

All required checks must pass against the exact final PR head.

Check both:

1. GitHub Actions.
2. GitForge's own pipeline.

A successful enqueue is not a successful execution.

A successful build is not a successful security audit.

A successful subset of tests is not a full release validation.

## Step 8 — Merge and clean up

Once all requirements are met:

- Merge using the repository's configured strategy.
- Verify the commit is on main.
- Confirm the main branch checks.
- Update the issue.
- Close superseded PRs.
- Remove safe-to-delete branches.
- Preserve unrelated WIP.
- Verify the next dependent PR is based on the updated main.

Do not deploy a change solely because its PR was merged.

## Step 9 — Verify operational behavior

For infrastructure changes, test on the actual Fedora runner environment.

Capture relevant service logs, queue metrics, resource measurements and recovery evidence.

Do not claim production validation from local unit tests alone.

# 14. PR and merge-conflict resolution policy

Treat PR cleanup as a continuous workstream, not a final administrative task.

For every open PR, classify it:

| Classification | Action |
|---|---|
| Valid and independent | Rebase, validate and merge |
| Valid but overlapping another PR | Consolidate or sequence |
| Partially superseded | Port unique changes and close after verification |
| Fully superseded | Close with replacement reference |
| Stale but valuable | Preserve and port selected work |
| Incorrect or unsafe | Document and replace |
| Blocked by infrastructure | Keep explicit blocker and evidence |

When resolving merge conflicts:

1. Identify which branch introduced the original behavior.
2. Determine whether main has already changed that behavior.
3. Read the entire surrounding implementation.
4. Preserve all valid functionality.
5. Avoid duplicate declarations and duplicate tests.
6. Check configuration contract compatibility.
7. Check migrations and API schema compatibility.
8. Run tests for both sides of the conflict.
9. Review the final diff manually.
10. Record the resolution in the PR.

Do not automatically choose `ours` or `theirs` for important files.

Never force-push over another agent's branch without understanding its ownership and current work.

If another agent is actively modifying the same subsystem, coordinate the branch boundary rather than competing with it.

# 19. Final instruction to the implementation agent

Treat this as a coordinated engineering programme with an emphasis on execution, not documentation.

Start by auditing and cleaning the current PR situation. Fix the correctness and security blockers before introducing risky optimizations. Preserve the useful smart-CI work, consolidate shared fixes, and establish reliable exact-commit validation.

Then implement the resource-aware scheduler, shared storage/workspace manager, incremental test intelligence, and benchmark-driven tooling improvements in that order.

Do not attempt to implement everything in one massive branch. Use focused PRs, dependencies, feature flags, controlled integration and measurable milestones.

Do not stop after making the first PR or resolving the obvious compile errors. Continue through the acceptance criteria and production validation.

**Most importantly: optimize GitForge as one coordinated system.**

The scheduler, runners, test framework, cache, filesystem, database and API should work together. A job should know what it needs; the scheduler should know whether it can safely run; the workspace manager should provision it efficiently; shared immutable storage should eliminate redundant data; the test graph should eliminate unnecessary execution; and observability should make every decision explainable.

The finished product must be demonstrably faster, more reliable, more efficient and safer under real multi-project workloads—not merely more sophisticated on paper.

Do not report production readiness until the final checklist is satisfied and the exact release candidate has passed its required validation.
