GitForge audit and proposed storage architecture
The repository is aliasfoxkde/GitForge, and I’m treating the current main branch as the production baseline while separately checking active development branches.

One important distinction: I would not approach this as merely a better Git worktree manager. The opportunity is to build a shared, content-addressed development and execution substrate that GitForge can use for repositories, build artifacts, dependencies, CI environments, agent sessions, and retained operational knowledge.

That could deliver substantially more value than adding symlink optimization to the existing checkout process.

The most important discovery is that GitForge already supports a Cargo cache mount in its own CI configuration.

The .gitforge.yml configuration mounts a host directory into containers at /cargo-target, with the host cache keyed by the CI image tag. It also explicitly treats a failed cache mount as an optimization failure rather than a correctness failure.

This is the right general principle, but it is not yet a unified cache architecture.
Existing implementation limitations
A. Cache storage is not a true content-addressed store.

crates/gitforge-storage/src/cache.rs currently identifies entries by a cache key and stores separate data and JSON metadata files.

It does not:
- Deduplicate identical content across different keys.
- Deduplicate content across repositories.
- Maintain reference counts for shared objects.
- Provide immutable objects with independently addressable references.
- Implement eviction based on global storage pressure.
- Provide a comprehensive integrity/reconciliation mechanism.
There is also a cache-key construction issue worth fixing: the key components are concatenated without explicit length or delimiter encoding, and the filesystem name uses only the first 16 hexadecimal characters of the resulting SHA-256.

B. The worktree problem is real, not hypothetical.

The October 10 worktree audit documented:
Condition	Count
Live worktrees	44
Clean	25
Dirty, 1–9 files	17
Additional dirty worktree	1
Build-artifact spill, 3,962 files	1

There was also an ownership problem: removing a dirty worktree could destroy another agent's active changes.

This is precisely the kind of lifecycle problem a proper manager should solve. It needs explicit ownership, leases, expiration, recoverability, and safe cleanup—not just git worktree prune.

Source: GitForge worktree audit.

C. There is already a storage reliability improvement in progress.

As of October 31, PR #336 proposes atomic file publication for artifacts, caches, receipts, and metadata.

That is important groundwork, but its stated semantics are deliberately narrower than a transactional storage engine: individual files are atomically published, while separate data and metadata renames are not a single transaction. Its full GitForge pipeline was still being validated in the PR description.

Source: PR #336 — Atomic storage publication.

I would build on that work rather than introduce another competing filesystem implementation.

2. The architecture I recommend
There are four major systems to build.









A. Resource-aware execution scheduler

Protect fast work and API responsiveness while controlling expensive jobs.

Issue #338












B. Shared CAS and workspace manager

Reuse immutable data, create cheap isolated workspaces and safely reclaim storage.

Issue #339












C. Incremental test and build intelligence

Determine what actually needs to execute and reuse proven results.

Issue #340












D. Optimized toolchain and execution adapters

Select the fastest compatible compiler, linter and test runner for each language.

Issue #341



A. Separate fast and heavy workloads
The key distinction is that GitForge shouldn't treat all jobs as equivalent.
Reserved capacity
Fast lane

Formatting, manifest checks, changed-file lint, targeted tests, small smoke tests and route validation.

Normal capacity
Standard lane

Ordinary compilation, builds and affected test suites.

Admission controlled
Heavy lane

Full-workspace builds, full tests, coverage, fuzzing, mutation testing and release builds.

Background lane

Cache warming, graph rebuilding, GC, log compaction and scheduled audits.


The scheduler will need more than priority labels. It should consider CPU, memory, disk space, I/O pressure, active jobs, repository concurrency and the cost of each job.

I specifically included:
- Weighted fairness between repositories and tenants.
- Reserved fast-lane capacity without starving heavy work.
- Per-repository concurrency limits.
- Durable queue reasons explaining why work is waiting.
- Cgroup-enforced resource reservations.
- Bounded pending work rather than unlimited waiting tasks.
- Separate control-plane responsiveness from compute workload.
This is especially important on a 2-core VPS. A machine that can technically start eight jobs does not necessarily have the resources to execute them efficiently.
B. The shared storage system
I recommend building a GitForge storage subsystem with three layers.
Immutable content-addressed store

Verified blobs · dependencies · build artifacts · logs · snapshots


Manifests and references
Ownership, versions, hashes and leases

Workspace providers
Git worktrees, reflinks, OverlayFS, Btrfs



Isolated execution environments

Independent agent sessions · CI jobs · builds · test runs


This borrows from pnpm's content-addressed package storage, but extends the concept.

pnpm's implementation illustrates several important constraints: hard links require the same filesystem, the shared store is a trust boundary, and integrity checks protect cached content. 

GitHub

For GitForge:
- Git retains ownership of Git objects.
- The CAS stores reusable non-Git data.
- Manifests connect logical workspaces and artifacts to immutable objects.
- Workspaces get independent writable state.
- Garbage collection follows references, leases and ownership.
- Reflink/OverlayFS/Btrfs are optional workspace backends.
Btrfs is particularly interesting because snapshots initially share copy-on-write extents, but snapshots are not backups. 

BTRFS documentation

An important distinction: do not hard-link mutable build outputs or concurrently share Cargo target directories. Use isolated writable outputs and compiler-level caching.
C. Incremental testing
I consider this one of the highest-value opportunities.

For example:

Suppose a project has 1,000 tests and you change a function used by 12 tests.

Instead of immediately executing all 1,000, GitForge should know which tests exercise that function and which dependent components might be affected.

The graph should track:
- Source files, functions, modules and packages.
- Static dependencies and reverse dependencies.
- Test-to-code execution relationships.
- Test inputs and fixtures.
- Compiler, runtime, image and environment identity.
- Previous results, failures and flaky behavior.
A test result should be reusable only if its entire relevant execution fingerprint matches.

New tests, failed tests, flaky tests, integration tests with unknown dependencies, and tests affected by global configuration changes must not be silently skipped.

I also specified differential validation: execute both the optimized test selection and the full suite on the same commit during rollout. Any missed failure blocks enabling test-result reuse.

There is already useful work to preserve here: the older #322 branch contains a graph implementation and changed-crate selection, but it is 70 commits behind main. We should rebase and review that work rather than recreate it.

A few important qualifications:
- Lust's current prototype does not support generics, traits or closures. Its reported agent edit-loop speedups are interesting, but it cannot replace rustc and Clippy for general production Rust projects.
- ts-rust reports substantial TypeScript checking improvements, including a 4.35x result against its TypeScript 7 baseline in one benchmark. However, it is an early release pinned to a particular TypeScript revision. Keep it advisory until exact diagnostics and compatibility are demonstrated on our projects.
- Nextest controls test concurrency, process isolation, retries and test groups. It complements Cargo rather than replacing Cargo.

- sccache has important Rust-specific limitations: incremental compilation is not cached, and some linker-dependent crate types are not cacheable.

- pytest-testmon is especially interesting because it tracks test-to-code dependencies using coverage data and selects tests affected by changed code. It also requires an initial full collection.

I would build an extensible test-runner interface and integrate your OpenTestSuite prototype through adapters rather than build a separate testing framework into GitForge itself. 
3. What should happen first?
I established this execution order in the epic.
1. Gate 0 — Correctness and security
   
   Resolve the SSH callback and API fixture compile errors, fix the GitForge polling authentication contract, complete cargo-vet audits, and resolve public PR runner isolation.
2. Gate 1 — Queue and resource observability
   
   Measure queue waiting time, host pressure, per-job resource consumption, storage usage and cache effectiveness. Implement bounded admission before increasing concurrency.
3. Gate 2 — Shared storage and workspaces
   
   Build the immutable object store and workspace provider, then benchmark native worktrees, reflinks, OverlayFS and Btrfs.
4. Gate 3 — Incremental validation
   
   Rebase #322, integrate per-test mappings, and compare optimized test selection against full tests.
5. Gate 4 — Toolchain optimization
   
   Benchmark alternative tools under identical workloads and roll out only those that improve performance without compromising correctness.

5. My overall recommendation
I would prioritize the work as follows:
Rank	Investment	Expected importance
1	Queue admission, host-pressure governance and fast/heavy lanes	Very high
2	Eliminate duplicate CI execution and redundant validation	Very high
3	Shared immutable dependency/build cache	Very high
4	Incremental test impact and verified result reuse	Very high
5	Managed copy-on-write workspaces and GC	High
6	Alternative compiler/linter/test tooling	Medium–high
7	Conversation/log knowledge compaction	High for long-term storage efficiency

The most important architectural decision is to avoid treating storage, scheduling and testing as separate optimizations.

They should cooperate:

A job should know what it needs, the scheduler should know whether it can safely run, the workspace manager should provision it efficiently, the CAS should reuse immutable inputs, and the test graph should avoid executing work that is demonstrably unnecessary.

That is a much more significant advantage than simply making Docker builds or individual compilers faster.

The immediate next implementation milestone should be Gate 0 and #338. Once the CI execution contract and resource observability are reliable, the storage and incremental-testing work can be introduced without creating another source of queue instability.
